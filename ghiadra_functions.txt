Verdict: GetAmount, IsIn(int,int) and IsInInv stay "safe in practice"

The chain is now seen down to the item constructor, and it matches the earlier verdict with one correction.

What the unpack does:

    oCWorld::CreateVob(0x81, instanceIndex) only logs when debug level is above 9. For type 0x81 (item) it calls oCObjectFactory vtable +0x3C with the instance index.
    That factory slot is unseen. It is almost certainly CreateItem(int), which news an oCItem and runs its script instance.
    zCParser::CreateInstance(int, void*) is seen. It does four things:
        looks up the symbol and checks that it is an instance (type 0x7000)
        stores the new object's pointer at symbol+0x1C (FUN_007a2f20)
        calls SetUseInstance
        runs the instance's bytecode with DoStack, which is the Daedalus instance ItMi_Gold(C_Item) { name = ...; } body

Correction to what I said before. I guessed the unpack might touch the ITEM global. It doesn't. It overwrites the item instance's own symbol (for example ITMI_GOLD) with a pointer to the new item. It also executes that instance's constructor bytecode. So CreateVob does run script code, though only the instance body, not a function call through CallFunc.

Why I still call it safe:

    The pointer overwrite is what the engine does on every item creation. Every item spawn, trade and loot drop rewrites that symbol. Nothing can depend on a previous value, and the new item is alive in the inventory.
    Instance bodies are normally plain field assignments. They write into the new item through that symbol's offset, so they touch only the new item.
    It is the engine's own path. Npc_HasItems takes it while a script is running, so the parser tolerates it.
    Totals are preserved.

What's still unproven:

    the factory slot +0x3C
    DoStack itself. I assume it runs the body without clearing the operand stack, unlike CallFunc. If it does clear it, it matters only mid-script.
    a mod whose item instance bodies call externals or other functions. That is rare. If you need certainty, the census could scan item instance bytecode for CALL/CALLEXTERN, and I can write that.

1. Answer on "parser idle"

Keep the rule for your own calls. DoStack shares the parser's operand stack and state, so running it from inside a running script or an external hook is the one case I can't vouch for. From Game_Loop or any plugin per-frame code it is fine. That is the same condition NnParserBusy() checks.
